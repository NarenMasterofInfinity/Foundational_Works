A diagram shows three boxes: input adapter, task service, and repository. A reviewer asks whether the application needs three servers. The author intended all three to be modules inside one program.

Both readers saw the same boxes but gave them different meanings. A useful system diagram must make its level of detail clear.

In this chapter: We will draw the to-do application from several viewpoints, trace a request, and use the drawings to find possible failures.

1.4.1 · Choose a view that answers a question

Suppose we want to explain the application to a new team member. We might begin with the person who uses it and the task system as a whole. A developer changing validation needs a closer view of the modules. Someone investigating a machine failure needs to see where the application and data run.

These are different views of the same system. Each selects the details needed for a particular question.

The C4 model names four levels for describing system structure: context, containers, components, and code. Moving through them is like zooming in on the application.

A container has a particular meaning in C4: an application or data store. It can be a browser application, a server application, or a database. It does not have to be a Docker container. The C4 container definition explains this terminology.

Sequence and deployment views add information about order and location. They support the four structural levels rather than adding more levels of zoom. We can use whichever views help explain the design.

1.4.2 · Show where the program and data live

Our first version was an in-memory script. The second used modules and a local database. Now the team needs to access tasks from several computers, so we add a web interface. A browser sends requests to the server application, which uses the task service and repository.

{{fig-2}}

The deployment view shows an important detail: the server application and SQLite file are on the same machine. The browser is elsewhere. If the server machine fails, both the application and access to its database are affected.

Parts that can fail together because of one cause belong to a failure domain. Here, the machine is a shared failure domain. Drawing the service and repository as separate boxes does not give them independent machines.

The browser also introduces a trust boundary. The server cannot assume that a request is valid merely because it came from the application’s usual web page. A user can construct requests directly.

The server must establish who the caller is; this is authentication. It must then check whether that caller may access the requested task; this is authorization. Every task operation needs the relevant check. Hiding another person’s task from the web page does not prevent a direct request for it. Unit 18 develops these checks in detail.

1.4.3 · Trace a request from input to reply

Let us create a task through the web interface. The browser sends POST /tasks with a JSON body containing {"title": "Read"}. The following sequence describes the intended API; the local Python example is not an HTTP server.

1. Identify the caller from a validated session.
2. Read the title and check the input.
3. Begin a database transaction.
4. Insert the task with the caller as its owner.
5. Commit the transaction.
6. Return:
   201 Created
   Location: /tasks/7
   {"id": 7, "title": "Read", "done": false}

The 201 Created response tells the client that creation succeeded. The Location header identifies the new resource. HTTP’s specification defines this response. Waiting for the database commit is an additional rule of our application.

Now interrupt the sequence. If title validation fails, the application writes no task. If the transaction fails before commit, the application reports an error. If the process crashes after commit but before the reply, task 7 exists even though the browser has not received success.

{{fig-3}}

What should the browser conclude after waiting too long for a reply? It cannot tell whether the task was saved. The request might never have reached the application, or the task might have been committed and the reply lost.

If the browser sends a fresh create request, the application may add task 8. The user intended one task but now has two. To recognise retries, the client and server need a stable identifier for the original operation. The server must store that identifier with its result so that a repeated attempt can retrieve the earlier result. Chapter 8.2 develops this mechanism, called request deduplication.

This is why event order belongs in the diagram. A drawing with only “request” and “response” can hide the commit that determines whether a task exists.

1.4.4 · Label arrows and copies of data

An arrow can mean a function call, a network request, a code dependency, or a step in a sequence. Label it with the actual relationship. For example, “HTTPS request,” “calls insert,” and “implements interface” describe different things.

Use a legend when colour or line style carries meaning. In this atlas, dashed arrows often show dependencies or zoom relationships, while solid arrows show the labelled action. Read the labels and caption to find the meaning in that particular view.

Also show where copies of data are held. The browser may display a task list it fetched a minute ago. The application may hold a task record in memory. The database contains the committed record. If another user completes a task, the browser’s old list does not update itself. We must decide when it fetches or receives new data.

A diagram that distinguishes these copies makes the freshness question visible. A single label saying “task data” does not tell us which copy a reader is seeing.

A closer look · Four ways to review a diagram
  1. Stop a component. What stops with it? If several modules share one process, a process crash affects all of them.
  2. Delay a call. Who is waiting? Decide how long that caller can wait and what happens when the time runs out.
  3. Repeat a request. Does it add another task? Point to the code and stored information that recognise a retry, if that behaviour is required.
  4. Change a data format. Which readers and writers must change together? Check how old and new versions will work during the update.

These questions help uncover omissions. Tests are then needed to check the actual behaviour.

1.4.5 · Change the design when there is a reason

{{fig-4}}

Each change in our example answered a particular need. Persistent storage let tasks survive a process restart. Modules gave shared rules a clear home. A web interface let people use the application remotely. None of these changes made it survive failure of its only machine.

Suppose the application becomes slow. Before adding another server, measure where requests spend their time. A slow database query may need a better query or index. Adding application servers could send even more work to that same query. If computation in the application is the bottleneck and storage has spare capacity, additional workers may help.

Adding a second machine also changes our storage assumptions. If each machine has its own unrelated task database, a user may see different lists depending on which machine handles the request. We need a design for shared or coordinated data; a load balancer alone cannot supply it.

The drawings help us review these consequences together. A structure view assigns responsibilities. A sequence view shows event order. A deployment view shows where execution and data live. They should describe a consistent design.

COMMON MISTAKES

Three module boxes need not mean three servers. A timeout does not establish that a write failed. And another application machine does not automatically provide another usable copy of the data.

Remember: Choose a diagram for a specific question. Label what the boxes and arrows mean. Check that the code structure, request sequence, and deployment tell the same story.
