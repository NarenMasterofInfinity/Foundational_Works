Our to-do application can now save tasks between runs. We add a web form and a command-line interface. Both contain code that checks the title. Later, we change the title limit from 80 characters to 200, but update only the web form.

The same application now accepts a title through one entry point and rejects it through another. To fix the cause, we need to decide where the rule belongs.

In this chapter: We will divide the application into modules, examine the dependencies between them, and follow a change through the revised design.

1.2.1 · Why does one change require several edits?

A first version of the web handler may do everything in one place: read the request, check the title, write SQL, and build the response. For a small program, this is easy to follow. The difficulty appears when another feature needs some of the same behaviour.

Suppose the command-line interface copies the title check. A CSV exporter also reads the database table directly. We now have two copies of a rule and several places that know how tasks are stored. Changing either the rule or the table can affect several features.

{{fig-1}}

Coupling describes the dependencies between parts of a system. In this example, the exporter is coupled to the database layout: it must know the column names. Rename a column, and its query may stop working.

A dependency is often necessary. The task service needs some way to store a task. The design question is how much it needs to know. Calling repository.insert(title) requires less knowledge of storage than constructing SQL and opening database files throughout the application.

Cohesion describes how closely the work inside a module belongs together. Checking task titles and completing tasks serve a shared purpose. Password handling, CSV formatting, and database connection setup have different purposes; placing them in a single “helpers” module gives that module little focus.

Coupling asks how one module depends on another. Cohesion asks whether the work within one module belongs together. These ideas help us decide where to put code.

1.2.2 · Separate input, task rules, and storage

Let us give the application three main responsibilities.

  • The input adapter translates an incoming request into a call the application understands. A web adapter reads an HTTP request; a command-line adapter reads command-line input.
  • The task service applies task rules. It checks the title and asks storage to create a task.
  • The repository provides operations for storing and retrieving tasks. Our SQLite implementation contains the database queries and commits each change before returning.
{{fig-2}}

This division is an example of separation of concerns: giving different kinds of work their own place. The web adapter handles web details, the service handles task rules, and the repository handles storage details.

Here is the essential structure. This is pseudocode, so it shows the responsibilities without implementing a complete web server.

interface TaskRepository:
    insert(title) -> saved Task, or StorageError
    list() -> list of Task records
    set_done(id) -> saved Task, or NotFound, or StorageError

class TaskService:
    constructor(repository):
        self.repository = repository

    create(raw_title):
        title = trim(raw_title)
        require 1 <= length(title) <= 200
        return self.repository.insert(title)

handle_http(request, service):
    title = parse_json(request.body)["title"]
    task = service.create(title)
    return response(201, json(task))

Follow a request through this code. The web adapter reads the title from JSON. The service checks it. The repository inserts and commits the task. The saved task returns through the service to the adapter, which builds the response.

The command-line adapter can call the same service.create(title). When the title limit changes, we update the shared rule. Each adapter still checks its own input format: for example, whether a web request contains valid JSON. Task rules and input-format rules have different jobs.

The real Python example implements the service and repository. It also checks that a title is text. A complete HTTP adapter would additionally handle missing fields, invalid JSON, and storage errors.

1.2.3 · Hide details that callers do not need

The service needs to request a saved task. It does not need to know the table name, SQL statement, or file path used to store it. The repository presents a simpler operation, insert(title), while hiding those details. This is abstraction.

The contract still matters. In our design, insert must return only after commit. The service relies on that behaviour when it returns success. An abstraction should hide implementation details while explaining the behaviour callers depend on.

ONE OPERATION, SEVERAL HIDDEN STEPS

The service asks “store this task.” The repository handles the query and commit needed to carry out that request.

Encapsulation controls access to a component’s internal data. If every part of the application can change the repository’s records directly, it can bypass the rules we have just defined. Returning a separate task record, rather than a reference that callers can use to edit internal state, helps preserve that control.

Modularity is the organisation of a system into parts with clear responsibilities and interfaces. Separate files can help, but the division is useful only if it limits what each part must know about the others. Ten files that all edit the same internal data can still be difficult to change.

{{fig-3}}

At application startup, we create the SQLite repository and pass it to the service: TaskService(SQLiteTasks(path)). Supplying a dependency this way is called dependency injection. The startup code that creates and connects these objects is sometimes called the composition root. Unit 6 examines these ideas in detail.

Read the dashed arrows in the figure as code dependencies: the service uses the repository contract, and the SQLite adapter implements it. During execution, the service calls that adapter. All of this can happen in one process, without a network call.

1.2.4 · Check the design by changing it

We can judge the division by asking where an edit would be needed. Consider four changes to the application.

Table 1.2.1 · Where should a change be made?
ChangeMain place to editWhat else needs checking?
Accept a web form instead of JSON.Web input adapter.Does it pass the same title to the service and display errors correctly?
Increase the title limit.Task service.Can the database store the longer title? Update any matching database constraint.

The last change affects several parts because it adds new behaviour. A caller must identify a repeated request, and storage must keep enough information to recognise it. Good modules help us see where agreement is needed; they cannot make every change fit inside one file.

1.2.5 · Understand what a layer hides

We can also arrange the application as a series of abstraction layers. Each layer uses the operations offered by the one below it. A user asks to remember a task. The application turns that into a storage operation. The storage implementation uses the operating system to read and write files.

{{fig-4}}

Each step lets us work at a different level of detail. When writing title validation, we do not need to reason about disk blocks. When investigating a damaged database file, those lower-level details may become important.

Some details must be visible in the contract. For example, suppose a repository returns results one at a time and keeps a database connection open until the caller finishes reading. A slow caller can then hold that connection for a long time. The caller needs to know when and how to close the result. Alternatively, the repository could return a bounded page of records and release the connection before returning.

A closer look · Why a test substitute cannot check persistence

We can test title validation using a simple repository that stores tasks in memory. This makes the test quick and easy to control. But the substitute loses its tasks when it is discarded. It cannot demonstrate that SQLite saves a task across a restart.

For that check, use the real repository: create a task, close the connection, open a new connection to the same database, and read the task. The two tests answer different questions. Matching method names does not mean that two implementations have the same behaviour in every situation.

1.2.6 · Use the amount of structure the application needs

In this example, separating the title rule helps because both the web and command-line interfaces use it. Keeping SQL in a repository helps because several features need tasks without needing to know the table layout. These are concrete reasons for the boundaries.

Every added interface also takes work to understand and maintain. A short, temporary script may need only a few functions. As the program grows, introduce a boundary where it protects a rule, hides a storage detail, or allows a real change to be made safely.

The modules still run in one application. If that process crashes, all of them stop. Code organisation improves how we understand, change, and test the application; keeping it running through a machine failure requires further design work.

COMMON MISTAKES

Separate files do not necessarily have separate responsibilities. An interface does not automatically hide useful details. And fewer dependencies are not always better: the application needs well-defined dependencies to get its work done.
