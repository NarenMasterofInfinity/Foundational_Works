Imagine that you have written a small to-do program. You enter “Read the design notes,” and the program adds it to your list. You close the program. When you open it the next morning, the list is empty.

The program could add a task, but it could not keep one. To make it useful, we must decide where tasks are stored and what should happen when the program stops. These are our first system design questions.

In this chapter: We will identify the parts of this application, follow a change in its data, and decide when it is safe to display “Saved.”

1.1.1 · What makes a program part of a system?

A software system consists of parts that work together to perform a task. In our example, the program accepts a title, checks it, stores a task, and displays the list. Once we add permanent storage, the program and the stored data must work together.

It helps to state what we are designing. Our first application is for one person using one machine. The person can add tasks, list them, and mark them complete. A task reported as saved must still be present after the program restarts. For now, we assume that the machine’s disk remains intact.

We can draw a line around the application and its storage. This is the system boundary: it tells us which parts we are considering together. The person uses the system from outside this line.

{{fig-1}}

The boundary depends on the question. To investigate a slow function, we may study only the running program. To investigate a missing task, we also need to examine storage. When drawing a boundary, state which question it helps answer.

System design is the work of deciding how these parts should be organised and how they should interact to meet the requirements. For our application, this includes choosing where to store tasks, which code checks their titles, and when to tell the user that a task has been saved.

1.1.2 · Follow one task through the program

Let us first keep tasks in memory. Memory holds the data used by a running program. In this example, the program creates a new, empty dictionary each time it starts.

The following Python code assumes that calls run one at a time, that the title is text, and that the caller supplies a positive integer identifier. It checks the title length and prevents two tasks from using the same identifier.

tasks = {}

def create(task_id, title):
    title = title.strip()
    if not 1 <= len(title) <= 200:
        raise ValueError("title must contain 1–200 characters")
    if task_id in tasks:
        raise ValueError("task id already exists")

    tasks[task_id] = {"title": title, "done": False}
    return {"id": task_id, **tasks[task_id]}

print(create(7, "  Read  "))
# {'id': 7, 'title': 'Read', 'done': False}

The call create(7, " Read ") first removes spaces from the ends of the title. It checks that the resulting title is between 1 and 200 characters long and that identifier 7 is unused. It then adds one task and returns its details.

Before the call, tasks is empty. After the call, it contains task 7. This is a state change. The state of a system is the information it currently holds that affects what it will do next. If we now ask for the task list, task 7 will appear because the state has changed.

{{fig-2}}

We can use this one operation to distinguish four related ideas. The title “Read,” the number 7, and the value False are data. The collection of tasks currently stored is state. Trimming and checking the title are computation. Passing the title into the function and returning the result are communication. Later, communication may also involve files or a network.

Some rules must hold whenever the task collection is valid: each task must have a unique identifier, and each title must contain 1–200 characters after trimming. A rule of this kind is called an invariant. If validation fails, the function raises an error before changing the collection.

To complete task 7, we would check that it exists and set tasks[7]["done"] = True. Setting that flag to True again leaves the task completed. Creating another task is different: it adds another entry. We will return to this distinction when we discuss repeated requests.

A closer look · Describing a state change with notation

We can write an operation as T(S, c) → (S′, result). Here, S is the state before the operation, c is the command, and S′ is the state afterward.

For our example, S is an empty task collection, c is “create task 7 with title Read,” and S′ contains that task. If the title is empty, the result is an error and S′ = S. This notation describes the intended change. By itself, it says nothing about crashes or two callers running at the same time.

1.1.3 · Decide what “saved” means

The dictionary works while the program is running. When the program restarts, it creates a new dictionary and loses the old list. To meet our restart requirement, we need persistent storage: storage that keeps data after the program stops.

For this application, we will use SQLite, a database that can store its data in a local file. The application groups a write into a transaction. Completing the transaction successfully is called a commit. We will report success only after the database has committed the task.

{{fig-3}}

The order matters. Suppose the application displays “Saved” and then tries to write the task. If it crashes between these events, the user has been told that a task was saved even though it is missing after restart. Waiting for commit avoids this particular failure.

This is a promise about restarting the program while its committed storage remains intact. If the only disk is destroyed, a local database cannot recover the data from that disk. The SQLite atomic-commit documentation explains how its commit mechanism works and which storage assumptions it relies on.

The model removes memory when the process restarts and keeps committed storage. It does not simulate a damaged disk or a power failure. The runnable Python example lets you create a task, close the real database connection, and read the task through a new connection.

1.1.4 · Give each part a clear contract

A component is a part of the system with a defined responsibility. We will soon separate the code that accepts input, the code that applies task rules, and the code that stores tasks. These components can all run inside the same program.

Components need a way to use one another. An interface describes the operations they offer, such as create(title) or list_tasks(). A contract explains how those operations behave.

For example, the name create(title) does not tell us whether blank titles are accepted or whether the result has already been saved. We must state those rules. The following contract describes the persistent version of our application, which will assign identifiers itself.

The last row introduces a problem we will examine in Chapter 1.4. Saving a task and delivering its reply are separate events. The application must account for both.

1.1.5 · Look at the same design at two levels

We can now ask two sets of questions. Where does the application store tasks, and how does it communicate with that storage? Within the application, which functions validate a title and perform the write?

{{fig-4}}

High-Level Design (HLD) usually describes the main parts of a system and how they work together. For our application, it shows the user, application, and persistent store. It also states that the application waits for commit before reporting success.

Low-Level Design (LLD) describes how a part is implemented: its functions, classes, interfaces, data structures, and algorithms. Here, it explains how the task service checks a title and calls the storage code.

Software architecture concerns the major choices that shape the system and the reasons for them. Choosing to keep tasks in a local database is one such choice. Different teams use HLD, LLD, and architecture somewhat differently; the useful distinction is the level of detail being discussed.

Both levels must agree. The high-level design may say “save before replying,” but the code must actually wait for the save to finish.

CHECK YOUR UNDERSTANDING

Putting a dictionary in a class does not make it persistent. Adding a database does not make a reply arrive. A successful restart test does not show what happens when the disk is destroyed. Each result depends on a different part of the design.

Remember: Start with what the application must do. Identify the parts and the data they hold. Then trace the events that must happen before the user receives success.
