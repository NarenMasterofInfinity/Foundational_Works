A request to “make the app production-ready” is not yet a design input. Should it survive a process crash, a destroyed laptop, a failed region, or a malicious administrator? Should a task appear in ten milliseconds or two seconds?

Each interpretation produces a different system. Requirements turn an argument about preferred technologies into a discussion about observable outcomes.

1.3.1 · Separate behavior from the conditions around it

A functional requirement specifies behavior the system must provide: create a task, list tasks, and complete a task. A nonfunctional requirement constrains the quality or conditions of that behavior: response latency, persistence, access isolation, operating cost, or ease of change. The distinction is useful but imperfect. Authorization may be specified as a function and also evaluated as a security property. Focus on the contract, not on winning a classification debate.

For the shared version of our application, let us write a concrete brief. These are illustrative assumptions, not measured facts: a team of 20 people, at most 5 requests per second during normal use, a single application machine, and a small operational budget. Users can create, list, and complete their own tasks. The service rejects malformed input. A reported successful creation survives restarting the application process while the storage system remains intact. List requests should complete within 300 ms for at least 95% of requests under the stated test workload.

That last requirement needs a measurement procedure: which endpoint, payload size, data volume, test duration, warm-up, client location, and error handling? We cannot responsibly translate “5 requests per second” into a server count without measuring per-request cost and defining headroom. Unit 2 provides the complete estimation method. 1.3.2 · Name constraints, assumptions, and risks

A constraint limits the solution space: use an existing machine, comply with a retention rule, finish within a calendar deadline. An assumption is a condition temporarily treated as true: the disk remains intact during process restart; a user does not submit unbounded titles. A risk is an uncertain event or condition that could undermine the outcome: the only host fails, a restore has never been tested, or traffic grows beyond the measured envelope. An assumption can itself become a risk when there is little evidence for it.

A trade-off is a choice among competing consequences. Local embedded storage simplifies operations but ties data placement to a host and limits some multi-instance deployment choices. A separate managed database can reduce some host coupling while adding network dependencies, cost, access controls, and migration work. Neither label alone establishes which choice is appropriate.

Architectural characteristics, often called quality attributes, describe properties such as performance, reliability, security, maintainability, and operability. Frameworks organize them differently. For example, the AWS Well-Architected framework offers a set of review lenses. Those are engineering guidance, not a theorem guaranteeing that an architecture is correct. Our cloud-neutral design uses such lenses to ask questions about an explicit workload.

1.3.3 · Feasibility first, preference second

Consider three candidates: memory-only storage, an embedded transactional store, and a separate database service. The first fails the restart requirement, so remove it before scoring preferences. A weighted decision matrix can help expose the remaining disagreements, but cannot prove an optimum. Scores are judgments; weights represent priorities, and their uncertainty matters.

1.3.4 · Write down why the choice makes sense

An Architecture Decision Record (ADR) captures one consequential choice and its rationale. A concise useful record includes context, status, the decision, consequences, and alternatives. Preserve the old rationale when a later decision supersedes it. Michael Nygard’s original ADR article describes this lightweight practice. The record below is an original example, not a universal template.

ADR 001 · ACCEPTED FOR THE TEACHING SCENARIO

Commit tasks in a local transactional store

Context
One small team, one host, low assumed traffic, process-restart persistence, no requirement for host-failure continuity.
Decision
Keep one application process with explicit modules. Use a local embedded database. Commit a task before reporting successful creation.
Alternatives
Memory-only state fails the restart promise. A separate database is feasible but adds an operating dependency that current evidence does not require.
Consequences
We gain a defined local commit boundary and simple deployment. Host or disk loss remains a service and data risk. Backups, restore tests, authorization, and monitoring remain necessary work.
Revisit when
Independent application replicas become necessary, measured write contention exceeds the latency budget, or the business requires recovery from loss of the host.
Evidence to collect
Restart tests, storage failure tests, a restore drill, and representative latency measurements.

The record avoids claiming that a database choice solves operations. It explicitly identifies the remaining work. “Revisit at 10,000 users” would be weaker than a trigger based on a measured bottleneck or a changed failure requirement: user count alone does not determine traffic, data size, or contention.

1.3.5 · Distinguish quality properties before combining them

{{fig-4}}

Availability concerns whether the service can provide the required response when called. Define what counts as an eligible request and a successful result before measuring it. Durability concerns the persistence of committed data under a stated failure model. Reliability is often used more broadly for correct service over time; usage varies, so state the operational definition. Consistency concerns the allowed observations of state across operations or copies and needs a precise contract in distributed settings.

A replica may increase read capacity while lagging behind writes. A service may return successful HTTP responses while silently discarding tasks. A store may reject requests during recovery yet preserve every committed row. These outcomes answer different questions. Do not use “highly available,” “reliable,” and “durable” interchangeably in a review.

Go deeper · The simplest sufficient design is conditional

“Simple” is not identical to the fewest boxes. One enormous function may have little infrastructure but complicated reasoning. A managed database may add a network hop while simplifying backups and operational ownership for a particular team. Count the complexity that people must understand, operate, and recover, not only the components in a diagram.

“Sufficient” means the design meets the agreed contract with evidence proportionate to its risk. It is not permission to ignore a security requirement because traffic is low. Nor is it a demand to anticipate every hypothetical future feature. Isolate likely changes where the cost is modest, record the uncertainty, and revisit when the evidence changes.

MISCONCEPTION

A weighted matrix cannot trade away a mandatory correctness property. Reject infeasible candidates first. Use scores to discuss preferences among feasible candidates, and investigate close or assumption-sensitive results.

FIELD NOTE

A good ADR can become more useful after it is superseded: it explains which assumption changed. That helps later engineers avoid reintroducing the same unsuitable choice under a different name.

Carry forward: Turn a desire into an observable scenario. Check hard constraints, compare costs, record assumptions, and define what evidence would change the decision.
