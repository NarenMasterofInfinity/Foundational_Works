The team asks us to make the to-do application “fast, safe, and easy to maintain.” These are reasonable goals, but they leave important questions unanswered. How fast should a task list appear? Which failures should saved tasks survive? What changes should be easy to make?

Before choosing a design, we need to turn these goals into requirements that people can understand and check.

In this chapter: We will write a small set of requirements, compare storage choices, and record why one choice fits our application.

1.3.1 · State what the application must do

A requirement states something the system must do or a condition it must satisfy. “A user can mark a task complete” describes behaviour. “A saved task remains after the application restarts” describes a condition that behaviour must meet.

Requirements about what the system does are called functional requirements. Requirements about qualities such as speed, security, and ease of maintenance are commonly called nonfunctional requirements. Both influence the design.

Consider a shared version of our application. For this example, assume a team of 20 people, one application machine, and a small budget. During normal use, the application receives at most 5 requests per second. These are teaching assumptions, rather than measurements of a real service.

The team needs to create, list, and complete tasks. Each person’s tasks are private. A successful save must survive an application restart, provided the committed storage remains intact. At least 95% of list requests should finish within 300 milliseconds under an agreed test workload.

The timing requirement gives us something to measure. If a test sends 1,000 list requests, at least 950 must finish within 300 milliseconds. To make results comparable, we must also specify where the test runs, how many tasks it lists, and how much traffic it sends. Unit 2 develops this measurement process.

Qualities such as performance, security, reliability, and maintainability are also called quality attributes or architectural characteristics. Their names help organise a review. A concrete scenario tells us what each one means for this application.

Some requirements fit more than one category. Checking whether a user may complete a task is application behaviour and part of its security. The classification is useful for organising work; the important step is to implement and check the requirement.

1.3.2 · Separate constraints, assumptions, and risks

Suppose the team says that the first version must run on an existing machine. That limits the choices available to us. Such a limit is a constraint. A fixed budget or a delivery deadline can also be a constraint.

We have assumed that the disk remains intact when the process restarts. An assumption is something we treat as true while making a decision. Writing it down makes clear where the reasoning applies.

Now suppose the only disk fails. We may lose the saved tasks. This is a risk: a possible event that could prevent the system from meeting its needs. The team must decide whether to accept it or change the design, for example by keeping recoverable copies elsewhere.

These terms answer different questions. A constraint asks what limits our choices. An assumption asks what our reasoning relies on. A risk asks what could go wrong. They often connect: relying on one intact disk exposes us to the risk of losing that disk.

1.3.3 · Compare choices against the requirements

We have three storage candidates. We could keep tasks only in memory, use an embedded database such as SQLite, or run a separate database service. An embedded database runs as part of the application rather than as a separate server; here, it stores data in a local file.

First check the mandatory restart requirement. Memory alone fails it. However easy the code is to write, that option cannot meet the agreed need.

{{fig-3}}

The other two candidates can meet this requirement with suitable commit behaviour and storage settings. We can then compare their costs and benefits. Embedded storage keeps deployment small. A separate database can be accessed by multiple application machines, but also needs a network connection, access controls, and operating work.

A choice between competing benefits and costs is a trade-off. Which cost is worth paying depends on the requirements and on the people who will operate the system.

The scores express judgments about fit for this example. They are not performance measurements. The low score for separating an embedded store from its application machine reflects our local-file setup, rather than a claim about every possible use of SQLite.

We can assign a weight to each preference. A higher weight means that preference matters more to the decision. A weighted score multiplies each preference score by its weight, adds the results, and divides by the sum of the weights.

If simplicity has weight 5 and the other two preferences have weight 1 each, the embedded store receives (5×5 + 1×2 + 1×1) / 7 = 4.00. The separate database receives (5×2 + 1×4 + 1×4) / 7 ≈ 2.57. With these priorities, the embedded store ranks higher.

1.3.4 · Record the decision and its reasons

A few months later, someone may ask why the team chose a local database. A short Architecture Decision Record (ADR) can preserve the answer. It records the situation, the decision, and the consequences. It should also say when the team needs to reconsider.

ADR 001 · ACCEPTED FOR THIS EXAMPLE

Use a local database and commit before reporting success

Situation
A small team uses one application machine. Tasks must survive a process restart. The current requirement does not include keeping the service available after that machine fails.
Decision
Use SQLite on the application machine. Keep input handling, task rules, and storage code in separate modules. Wait for commit before returning success.
Alternatives
Memory alone fails the restart requirement. A separate database is possible, but its extra operating work is not yet justified by the requirements.
Consequences
Deployment is small, and the application has a clear point at which a task is committed. Losing the machine stops the service. Losing its only disk can lose data. We still need backups, restore checks, access controls, and monitoring.
Reconsider when
The application must run on several machines, measured storage contention causes unacceptable delays, or tasks must survive loss of the machine or disk.
Checks to run
Create a task and restart the process. Simulate a storage error. Restore a backup. Measure request times with representative data and traffic.

An ADR need not be long. It needs enough detail for a later reader to understand why the choice made sense. Michael Nygard’s article on documenting architecture decisions describes this practice.

If the requirements change, keep the old record and write a new one that replaces it. The earlier decision helps explain which assumption or need has changed.

1.3.5 · Distinguish the qualities we are checking

Some quality terms sound interchangeable. We need to separate them because they require different checks.

{{fig-4}}

Availability concerns whether the system can provide the required service when needed. If users cannot list their tasks while the application restarts, it is unavailable for that operation during that interval. When measuring availability, define which requests count and what a useful response is.

Durability concerns whether committed data survives specified failures. Our restart test checks whether a saved task remains after the process stops and starts. It says nothing about losing the only disk.

Reliability usually refers more broadly to providing correct service over time. Teams sometimes use it differently, so a requirement should explain the failures and outcomes it covers.

Consistency concerns which observations of state the system allows. For example, after completing a task, should the user’s next list request show it as complete? If the application later has several copies of the data, we must specify when each copy may show the change. Unit 14 examines precise consistency models.

These distinctions explain two possible outcomes. An application may keep replying to requests yet lose tasks it held only in memory. A database may preserve every committed task while refusing requests during recovery. The first has a data-loss problem; the second has a period of unavailability.

A closer look · What makes a design simple enough?

Count the work needed to understand, change, operate, and recover the system. One large function may use few components yet be hard to maintain. A separate managed database may add a network connection while reducing backup work for a team.

The simplest sufficient design meets the agreed requirements with manageable work. Low traffic does not remove the need for access controls or correct saves. At the same time, an imagined future need does not automatically justify extra infrastructure today. Record likely changes and the conditions that would make them necessary.

COMMON MISTAKES

A high preference score cannot compensate for a failed requirement. More users do not, by themselves, tell us which part needs scaling. And a good uptime figure does not show whether saved data survives a failure.

Remember: Write requirements that can be checked. Reject choices that fail them. Compare the remaining choices, then record the reasons and the conditions for reconsidering.
