PART I / UNIT 01 / CHAPTER 1.1

A system is a promise

Prerequisite: Basic programming4 original figures · 1 workbench
Blue: normal flowGreen: healthyAmber: cautionRed: failurePurple: control / infrastructureGray: external / inactiveSolid arrow: action / data · dashed: dependency or zoom · dotted: acknowledgment

You write a small program that remembers tasks. It accepts “Read the design notes,” displays a success message, and lists the task. Then you close the program. The next morning, the list is empty.

The program did exactly what its instructions said. The system failed the promise the user thought it made. System design begins in that gap: between executing code and delivering dependable behavior in a real environment.

THE QUESTION

What must remain true after the happy path ends?

1.1.1 · Start with behavior, then draw the boundary

A software system is a collection of cooperating elements, considered within a boundary, that delivers behavior to its environment. The elements can include code, processes, stored data, devices, and external services. A useful boundary is chosen for a question: the application process is one system for a runtime discussion; the application plus database is another for a user-facing reliability discussion. Neither boundary is universally correct.

Our first scope is deliberately small. One person can create a task, list tasks, and mark a task complete. A successful creation must survive an ordinary application restart. We assume one machine, a functioning local disk, and one user. We have not promised survival of disk destruction, remote sharing, or global availability. Those are different requirements with different costs.

Designing this system means choosing responsibility, representation, interactions, and operating assumptions so that these behaviors hold. A diagram is evidence about a design, not the design itself. A box labeled “database” does not answer when success is returned, what happens on a failed write, or who restores a broken file. Those choices are part of the system.

1.1.2 · The simplest working implementation

A collection in memory is sufficient if tasks need exist only during one run. This miniature uses explicit identifiers so the state changes are easy to inspect. The caller chooses an unused positive integer; a production API would need an identity policy. The function returns a fresh snapshot so callers cannot silently change internal state through the returned object.

tasks = {}

def create(task_id, title):
    title = title.strip()
    if not title:
        raise ValueError("title must not be empty")
    if task_id in tasks:
        raise ValueError("task id already exists")
    tasks[task_id] = {"title": title, "done": False}
    return {"id": task_id, **tasks[task_id]}

print(create(7, "  Read  "))
# {'id': 7, 'title': 'Read', 'done': False}

Completion is the transition tasks[7]["done"] = True, after checking that task 7 exists. Repeating that assignment has the same task-state effect as doing it once. Repeating an unkeyed creation is different: it may create another task. The downloadable example implements both creation and completion with a commit before returning.

The mechanism is straightforward: normalize input, check the invariant, insert a record, and return the result. An invariant is a condition required to hold in every valid state: here, task identifiers are unique and titles are nonempty after trimming. This implementation assumes sequential calls. Under concurrent execution, checking an identifier and then inserting it is a compound operation that would need coordination. We will not claim it is thread-safe.

A SMALL FORMAL MODEL

Let S be the map from task identifiers to records, and c a command. Model execution as T(S, c) → (S′, result). Validation failure leaves the state unchanged. A create with a new identifier extends the map by exactly one entry. This is a useful model of behavior; it abstracts away scheduling, I/O, and crashes.

Data is a representation: the characters “Read,” an identifier, a Boolean. State is the information whose current value affects future behavior: the set of tasks currently stored. Computation transforms or examines data, such as validating a title. Communication transfers information across a boundary, such as a function call, a filesystem operation, or a network request. A single operation can involve all four. Distinguishing them helps locate both ownership and failure.

1.1.3 · Components, interfaces, and contracts

A component is a unit of responsibility chosen for the design. In the next chapter we will separate input handling, task rules, and storage. A component does not necessarily mean an independently deployed service. It might be a module, an object, or a group of functions in one executable.

An interface names the operations a collaborator can use. A contract adds meaning: accepted inputs, observable outputs, failure outcomes, and obligations. The signature create(title) → Task is insufficient. Does it trim whitespace? Is an empty title rejected? Does returning imply persistence? What does a timeout mean? A caller must know these answers to use the operation correctly.

Notice that an error at the communication boundary need not mean the business action failed. A client can time out after a task was saved. To guarantee a deduplicated retry, we would need an additional identity and retention contract. Merely labeling a function “idempotent” does not implement that mechanism. Chapter 8.2 is assigned that deeper treatment.

1.1.4 · High-level and low-level views meet at the contract

High-Level Design (HLD) commonly describes major components, data placement, communication, deployment, and quality trade-offs. Low-Level Design (LLD) commonly describes the internal modules, interfaces, types, algorithms, and collaboration that realize those responsibilities. Software architecture concerns consequential structural and behavioral choices and their rationale. Communities draw these boundaries differently. None of these labels is a universal formal partition of engineering work.

For example, HLD might say that the application commits tasks to a local store before acknowledging creation. LLD decides how the service receives a repository, validates a task, calls a transaction, and maps an error. They describe the same promise at different resolutions. A beautifully organized service class cannot correct an architecture that acknowledges volatile state as durable.

1.1.5 · Break the happy path on purpose

Restart the in-memory program and its map is initialized again. Moving the map into another class changes code organization but does not change that outcome. Writing JSON directly to a file helps with ordinary restarts, but introduces new questions: can a crash leave half a document, do concurrent writers overwrite each other, and what does “write completed” mean for the device? A durable embedded database is a reasonable next choice for this example because it provides a defined transaction mechanism. Its guarantees still depend on configuration and the storage stack. SQLite’s atomic-commit documentation explains those assumptions; it is not a guarantee against every possible hardware failure.

    Go deeper · Safety, progress, and observable evidence

    “Never acknowledge an uncommitted task” is a safety property: it excludes a bad execution. “Eventually finish a valid request” is a progress requirement that also depends on resource availability and the environment. A program that never replies can satisfy the first property while being useless. Conversely, immediately replying to every request can provide apparent progress while violating persistence.

    A system review should ask which observations would falsify each claim. Restarting the application tests one failure class. It does not test loss of the database disk. Restoring a backup tests another behavior. It does not prove that every recent write reached that backup. This habit of pairing a claim with its boundary and evidence will matter again in reliability and validation.

    MISCONCEPTION

    “It worked once” establishes one successful execution. It does not establish the contract for retries, restarts, bad inputs, or competing callers. Design the allowed histories, not just one screenshot of success.

    FIELD NOTE

    A database transaction and an HTTP response are two different events. There is no magic line of application code that makes the user’s knowledge update atomically with a commit on another machine. This small gap drives much of the later discussion of idempotency and reconciliation.

    Carry forward: A system is a promise made under assumptions. Find the state, name its owner, and identify the event after which success is justified.

    Before continuing: If a task survives a process restart, which failure has been tested—and which three failures are still untested?

    PART I / UNIT 01 / CHAPTER 1.2

    Boundaries that make change local

    Prerequisite: Chapter 1.14 original figures · 1 workbench
    Blue: normal flowGreen: healthyAmber: cautionRed: failurePurple: control / infrastructureGray: external / inactiveSolid arrow: action / data · dashed: dependency or zoom · dotted: acknowledgment

    The to-do program now persists its list. A teammate adds a CSV export. Another adds a web form. Each copies the same rule for trimming titles, and both reach directly into the stored records. A tiny schema change breaks three features.

    The immediate problem is change propagation. The next design step is to place knowledge where it can change safely.

    1.2.1 · First diagnose what is coupled

    Imagine one handler that parses an HTTP body, validates a title, constructs an SQL statement, commits a connection, and generates HTML. Initially this is easy to follow. With two entry points, the validation rule is copied. With CSV export, persistence layout escapes into another feature. A title-length policy is now enforced inconsistently, and changing the column name requires coordinated edits.

    Coupling is the dependency between elements: what one must know or assume about another. The number of arrows is only a clue. One dependency on a stable, narrow interface can be easier to maintain than one dependency on a mutable global structure with undocumented ordering rules. Temporal coupling—“call initialize before save”—can be dangerous even when there are few imports.

    Cohesion concerns how strongly the elements within a module serve a focused purpose. A task service that validates and coordinates task operations has a coherent responsibility. A helper module containing CSV formatting, database connection management, and password logic has little such focus. These are design judgments supported by change scenarios, not universal numerical scores. High cohesion does not mean a class must contain exactly one method.

    1.2.2 · Separate what changes for different reasons

    Our first revision uses three responsibilities. The input adapter understands transport syntax. The task service understands task rules. The repository understands persistent representation. The service returns application data; adapters choose whether to render HTML, JSON, or text. This is separation of concerns: organizing around distinct responsibilities while making their coordination explicit.

    # Language-neutral pseudocode; all calls remain in one process.
interface TaskRepository:
    insert(title) -> committed Task or StorageError
    list() -> list of Task snapshots
    set_done(id) -> committed Task or NotFound or StorageError

class TaskService:
    constructor(repository):
        self.repository = repository

    create(raw_title):
        title = trim(raw_title)
        require 1 <= length(title) <= 200
        return self.repository.insert(title)

handle_http(request, service):
    title = parse_json(request.body)["title"]
    task = service.create(title)
    return response(201, json(task))

    The implementation must handle missing fields, invalid JSON, unsupported content types, and storage errors at the adapter boundary. We omit those mechanics in this sketch to isolate responsibility; the executable Python example provides actual validation and commit behavior without pretending to be a complete web server.

    Now a command-line adapter can call the same service. A CSV exporter reads snapshots from the repository and formats them without mutating task state. The rule has one authoritative owner. If storage also enforces a constraint, that is deliberate defense of an invariant at another boundary; it is not a second, unrelated business-policy implementation.

    1.2.3 · An abstraction is a promise with hidden details

    Abstraction presents the behavior a caller needs while suppressing details irrelevant to that caller. The service needs “insert and return a committed task,” not “open this file, acquire this lock, and encode these bytes.” Encapsulation restricts access to the representation so that callers cannot bypass its invariants. An interface without encapsulation is weak: if every module can mutate the repository’s internal map, its save contract is easily circumvented.

    Modularity means the system has separable units with explicit responsibilities and controlled dependencies. Files are a tool for modularity; ten files that share every internal variable are not ten independent modules in a useful engineering sense. Our test is concrete: if the persistent layout changes, which application responsibilities must change with it?

    A USEFUL ANALOGY

    A module interface resembles a service counter: a caller requests a result without entering the workshop. The analogy stops at failures and timing. Software callers still need to know whether an operation can block, throw, time out, or partially complete.

    The diagram distinguishes source dependencies from runtime calls. The service is written against the repository contract. A concrete SQLite adapter implements it. The composition root is the place where the application constructs and connects these objects. At runtime, calling the interface executes the adapter. This does not require a dependency-injection container or a remote repository service. Passing an argument is sufficient.

    This boundary is useful if two implementations serve a real need: an in-memory test double for fast rule tests and a persistent adapter for the application. It costs extra types, contracts, and integration testing. If the program is a 20-line disposable script, an explicit parameter and a few functions may be clearer. Do not introduce a framework just to demonstrate a principle.

    1.2.5 · Layers reduce detail, not responsibility

    An abstraction layer offers one vocabulary to the layer above and relies on another below. “Remember a task” becomes an application operation, then a storage transaction, then filesystem and device actions. Different diagrams may show different layers. A source-level dependency rule need not follow the same direction as a runtime data path.

    Abstractions leak when their hidden assumptions become relevant. A repository interface returning a lazy cursor may keep a database connection alive while an HTTP client slowly reads results. The service has acquired a resource-lifetime obligation it did not anticipate. A clearer contract might return a bounded materialized page or explicitly expose a streaming lifetime with cancellation. A simple method name does not make the underlying resource cost disappear.

    Go deeper · Behavioral substitution beats matching signatures

    Suppose a memory repository and a disk repository both implement insert(title). The first returns after mutating memory; the second returns after commit. They match syntactically but differ on persistence. A memory double is suitable for testing title validation, but cannot validate durability. Integration tests must exercise the actual adapter and its storage configuration.

    Likewise, an adapter that accepts a transaction but commits every operation internally cannot substitute for one that promises atomic multi-operation work. The contract must identify the transaction owner. Interface compatibility includes behavior, errors, lifetime, and concurrency assumptions—not just argument types. Unit 6 will develop dependency lifetimes, and Unit 10 will develop transaction boundaries.

    1.2.6 · The engineering trade-off

    The revised design reduces the knowledge each collaborator needs. It adds indirection and requires someone to maintain the contracts. Prefer a boundary where there is a clear reason for independent change, an invariant to protect, or a resource whose ownership needs to be explicit. Do not maximize the number of interfaces. A module that merely forwards every call without hiding knowledge may add navigation cost without improving the design.

    Operationally, these modules still share a process and a failure domain. A repository that blocks forever can stall the service. An unbounded list query can exhaust memory. Module organization helps reasoning and testing; it does not automatically deliver overload control or availability. Extracting every module into a service would add network uncertainty, deployment coordination, and observability needs. That choice requires separate evidence.

    MISCONCEPTION

    “Low coupling” does not mean no dependencies. A functioning system requires collaboration. Prefer dependencies whose meaning is narrow, stable enough for the task, and explicit about behavior.

    RESEARCH NOTE

    Parnas’s 1972 modularization paper compares different ways to divide the same system. Its lasting lesson is to examine the criteria behind the division, rather than assume that one module per processing step is necessarily best. Our to-do example is an original application of that design question. Read the original paper record ↗

    Carry forward: Put knowledge behind a contract where there is a reason for it to change independently. Then test both the local rule and the real integration.

    Before continuing: If a repository starts returning results before they commit, which callers can break even though its method signature stays the same?

    PART I / UNIT 01 / CHAPTER 1.3

    Requirements become decisions

    Prerequisite: Chapter 1.24 original figures · 1 workbench
    Blue: normal flowGreen: healthyAmber: cautionRed: failurePurple: control / infrastructureGray: external / inactiveSolid arrow: action / data · dashed: dependency or zoom · dotted: acknowledgment

    A request to “make the app production-ready” is not yet a design input. Should it survive a process crash, a destroyed laptop, a failed region, or a malicious administrator? Should a task appear in ten milliseconds or two seconds?

    Each interpretation produces a different system. Requirements turn an argument about preferred technologies into a discussion about observable outcomes.

    1.3.1 · Separate behavior from the conditions around it

    A functional requirement specifies behavior the system must provide: create a task, list tasks, and complete a task. A nonfunctional requirement constrains the quality or conditions of that behavior: response latency, persistence, access isolation, operating cost, or ease of change. The distinction is useful but imperfect. Authorization may be specified as a function and also evaluated as a security property. Focus on the contract, not on winning a classification debate.

    For the shared version of our application, let us write a concrete brief. These are illustrative assumptions, not measured facts: a team of 20 people, at most 5 requests per second during normal use, a single application machine, and a small operational budget. Users can create, list, and complete their own tasks. The service rejects malformed input. A reported successful creation survives restarting the application process while the storage system remains intact. List requests should complete within 300 ms for at least 95% of requests under the stated test workload.

    That last requirement needs a measurement procedure: which endpoint, payload size, data volume, test duration, warm-up, client location, and error handling? We cannot responsibly translate “5 requests per second” into a server count without measuring per-request cost and defining headroom. Unit 2 is assigned the complete estimation method. Here we are learning to identify missing evidence.

    1.3.2 · Name constraints, assumptions, and risks

    A constraint limits the solution space: use an existing machine, comply with a retention rule, finish within a calendar deadline. An assumption is a condition temporarily treated as true: the disk remains intact during process restart; a user does not submit unbounded titles. A risk is an uncertain event or condition that could undermine the outcome: the only host fails, a restore has never been tested, or traffic grows beyond the measured envelope. An assumption can itself become a risk when there is little evidence for it.

    A trade-off is a choice among competing consequences. Local embedded storage simplifies operations but ties data placement to a host and limits some multi-instance deployment choices. A separate managed database can reduce some host coupling while adding network dependencies, cost, access controls, and migration work. Neither label alone establishes which choice is appropriate.

    Architectural characteristics, often called quality attributes, describe properties such as performance, reliability, security, maintainability, and operability. Frameworks organize them differently. For example, the AWS Well-Architected framework offers a set of review lenses. Those are engineering guidance, not a theorem guaranteeing that an architecture is correct. Our cloud-neutral design uses such lenses to ask questions about an explicit workload.

    1.3.3 · Feasibility first, preference second

    Consider three candidates: memory-only storage, an embedded transactional store, and a separate database service. The first fails the restart requirement, so remove it before scoring preferences. A weighted decision matrix can help expose the remaining disagreements, but cannot prove an optimum. Scores are judgments; weights represent priorities, and their uncertainty matters.

    1.3.4 · Write down why the choice makes sense

    An Architecture Decision Record (ADR) captures one consequential choice and its rationale. A concise useful record includes context, status, the decision, consequences, and alternatives. Preserve the old rationale when a later decision supersedes it. Michael Nygard’s original ADR article describes this lightweight practice. The record below is an original example, not a universal template.

    ADR 001 · ACCEPTED FOR THE TEACHING SCENARIO

    Commit tasks in a local transactional store

    Context
    One small team, one host, low assumed traffic, process-restart persistence, no requirement for host-failure continuity.
    Decision
    Keep one application process with explicit modules. Use a local embedded database. Commit a task before reporting successful creation.
    Alternatives
    Memory-only state fails the restart promise. A separate database is feasible but adds an operating dependency that current evidence does not require.
    Consequences
    We gain a defined local commit boundary and simple deployment. Host or disk loss remains a service and data risk. Backups, restore tests, authorization, and monitoring remain necessary work.
    Revisit when
    Independent application replicas become necessary, measured write contention exceeds the latency budget, or the business requires recovery from loss of the host.
    Evidence to collect
    Restart tests, storage failure tests, a restore drill, and representative latency measurements.

    The record avoids claiming that a database choice solves operations. It explicitly identifies the remaining work. “Revisit at 10,000 users” would be weaker than a trigger based on a measured bottleneck or a changed failure requirement: user count alone does not determine traffic, data size, or contention.

    1.3.5 · Distinguish quality properties before combining them

    Availability concerns whether the service can provide the required response when called. Define what counts as an eligible request and a successful result before measuring it. Durability concerns the persistence of committed data under a stated failure model. Reliability is often used more broadly for correct service over time; usage varies, so state the operational definition. Consistency concerns the allowed observations of state across operations or copies and needs a precise contract in distributed settings.

    A replica may increase read capacity while lagging behind writes. A service may return successful HTTP responses while silently discarding tasks. A store may reject requests during recovery yet preserve every committed row. These outcomes answer different questions. Do not use “highly available,” “reliable,” and “durable” interchangeably in a review.

    Go deeper · The simplest sufficient design is conditional

    “Simple” is not identical to the fewest boxes. One enormous function may have little infrastructure but complicated reasoning. A managed database may add a network hop while simplifying backups and operational ownership for a particular team. Count the complexity that people must understand, operate, and recover, not only the components in a diagram.

    “Sufficient” means the design meets the agreed contract with evidence proportionate to its risk. It is not permission to ignore a security requirement because traffic is low. Nor is it a demand to anticipate every hypothetical future feature. Isolate likely changes where the cost is modest, record the uncertainty, and revisit when the evidence changes.

    MISCONCEPTION

    A weighted matrix cannot trade away a mandatory correctness property. Reject infeasible candidates first. Use scores to discuss preferences among feasible candidates, and investigate close or assumption-sensitive results.

    FIELD NOTE

    A good ADR can become more useful after it is superseded: it explains which assumption changed. That helps later engineers avoid reintroducing the same unsuitable choice under a different name.

    Carry forward: Turn a desire into an observable scenario. Check hard constraints, compare costs, record assumptions, and define what evidence would change the decision.

    Before continuing: What observation would justify revisiting ADR 001 even if the system still had only 20 users?

    One application, many architectural views

    Prerequisite: Chapter 1.34 original figures · 1 workbench
    Blue: normal flowGreen: healthyAmber: cautionRed: failurePurple: control / infrastructureGray: external / inactiveSolid arrow: action / data · dashed: dependency or zoom · dotted: acknowledgment

    A reviewer points at the architecture diagram and asks, “Are those three boxes three servers?” The author meant three modules. Another arrow means a compile-time dependency; the reviewer thinks it is an HTTP call.

    A useful diagram answers a specific question and tells the reader how to interpret every boundary and arrow.

    1.4.1 · Choose the view for the question

    A static structure view shows elements and relationships. A sequence view shows ordered interactions in a scenario. A deployment view places executable artifacts and data on infrastructure. They can describe the same application while revealing different facts. A single diagram containing users, methods, disks, regions, and classes usually mixes too many levels to reason clearly.

    The C4 model’s original documentation defines four static abstraction levels: system context, containers, components, and code. Use the levels that help the audience. Sequence or dynamic views and deployment views provide additional perspectives rather than extra steps in that four-level hierarchy.

    Ask the same application four questions

    1.4.2 · Progress from a script to a small deployed application

    Let us make the evolution concrete. Version A is the in-memory script. It is sufficient for ephemeral session notes. Version B keeps the same local interaction but separates task rules from storage and commits to an embedded database. Version C introduces an HTTP adapter because multiple people need remote access. The task rule remains in the service. The storage adapter remains responsible for the commit.

    Introducing remote access changes the obligations. The input is untrusted, transport can fail, requests can repeat, identities matter, and requests may overlap. If tasks are private to their owners, every task operation needs an authorization check tied to the authenticated identity. Hiding an identifier in the UI is not access control. That requirement must be enforced server-side for list, read, completion, and deletion. Unit 18 is the planned threat-modeling and isolation treatment; the simple local Python exercise intentionally handles only one trusted local user.

    This deployment uses one machine and one local store. It has no redundancy. The browser and application are separated by a trust and network boundary; the service and repository are modules in the same process. The database file resides on the host. Moving the web application to two hosts while keeping a local file on only one does not create a working shared-data design. A change in deployment can invalidate an earlier storage assumption.

    1.4.3 · Trace an actual creation request

    # Illustrative API contract, not a running HTTP server.
POST /tasks
Content-Type: application/json
Body: {"title": "Read"}

1. Authenticate the caller; obtain owner identity from the session.
2. Parse and bound the input; reject invalid syntax or title.
3. Begin a storage transaction.
4. Insert task owned by the authenticated caller.
5. Commit the transaction.
6. Return 201 Created, Location: /tasks/7,
   and {"id": 7, "title": "Read", "done": false}.

    The response is sent after commit. If validation fails, no task is written. If the transaction fails before commit, no success is sent. If the process crashes after commit but before step 6, the task exists and the caller may see only a disconnection. If the network loses step 6, the application can be completely healthy while the caller still lacks the result. RFC 9110 defines the HTTP 201 response semantics; our commit ordering and duplicate-handling policy are additional application contracts.

    This is the reason sequence diagrams need explicit ordering. Two unlabeled arrows labeled “request/response” would hide the decisive event: the durable commit. The diagram also needs to say what has not been implemented. Here, a retry is a new creation. To deduplicate, the client would supply a stable operation identity; the server would bind it to the request and committed result with an appropriate atomicity and retention policy. We defer that full mechanism to 8.2 and the payment case study.

    1.4.4 · Make arrows and state copies explicit

    Use a solid blue arrow for the normal request or data flow, a dashed purple arrow for a source dependency or a zoom relationship, and a dotted arrow for an acknowledgment when that is the chosen legend. Label the action: “HTTPS create,” “commit task,” “implements protocol.” Place a legend alongside a view if color or line style carries meaning. A red boundary alone is inadequate; label the failure or trust property in words.

    State locations deserve special care. The browser may display a local snapshot. The server may hold an in-memory object. The database holds the committed record. Those are different copies with different lifetimes. After another user changes a record, the browser’s displayed copy can be stale even if the database is behaving correctly. A diagram that labels all three copies simply “task data” conceals the freshness contract.

    Go deeper · A diagram review with four adversarial questions
    1. Kill one box. If the host fails, which other boxes disappear with it? Logical boundaries do not imply independent failure.
    2. Delay one arrow. Which caller waits, for how long, and who owns cancellation? A synchronous dependency consumes a caller’s time budget.
    3. Repeat one message. Does the state change twice? If not, where is duplicate identity stored and how long is it retained?
    4. Change one representation. Which collaborators must deploy together? An apparently modular diagram can hide shared schemas or ordering assumptions.

    These are tests of the explanation, not complete failure proofs. Later units add transaction anomalies, replication histories, security threats, and workload tests to the same review habit.

    1.4.5 · Evolution requires a reason and a review

    Suppose the shared service eventually misses its latency objective. First locate the bottleneck. If the database is waiting on one slow query, adding application replicas can increase pressure without improving completion rate. If CPU work dominates and the state path has headroom, more application workers may help. If the availability requirement changes to survive a host failure, the design must address both execution and state placement. “Add servers” is an action, not an argument.

    Our first design review is therefore conditional. The current design is reasonable for its declared small, single-host scenario. It remains exposed to host loss, disk loss, untested restores, unknown concurrent-load behavior, and repeated creates after lost replies. The next production stages must either resolve those exposures or explicitly accept them against requirements. A list of famous infrastructure products would not supply that reasoning.

    MISCONCEPTION

    A module diagram is not a deployment topology. Three components inside a single process still share memory pressure, process crashes, and the host’s failure domain.

    FIELD NOTE

    The most useful annotation on an architecture drawing is often a short assumption: “one writer,” “commit before response,” “same host,” or “snapshot may be stale.” It tells a future reviewer exactly where to push.

    Carry forward: Use a structure view to assign responsibility, a sequence to expose ordering, and a deployment view to locate failures. Check that the three tell the same story.

    Before continuing: Which diagram would reveal an accidental success-before-commit bug? Which would reveal that the application and its backup share the same disk?

    UNIT 01 / EXPLAINED ANSWERS

    Solutions & reasoning

    Each explanation identifies the relevant assumption and why a tempting alternative fails.

    C1

    A program reports “saved” after adding a task to a map. Which contract can it satisfy, and which contract does it fail?

    It can satisfy a session-only create-and-list contract under sequential execution. It fails the chosen process-restart persistence promise because the next process constructs a new map. Renaming the map a repository or putting it behind an interface changes organization, not persistence.

    ← Return to question
    C2

    How does a method signature differ from a behavioral contract?

    The signature identifies inputs and outputs at the type level. The contract also states validation, side effects, errors, commit timing, retry behavior, and concurrency or lifetime assumptions. Two insert(title) methods can be incompatible if one returns before commit and the other promises persistence.

    ← Return to question
    C3

    Does low coupling require removing all dependencies?

    No. Useful behavior requires collaboration. Reduce unnecessary knowledge and make necessary obligations explicit. One dependency on a global mutable schema can cause more change propagation than several narrow stable interfaces. An interface that hides neither knowledge nor responsibility may merely add indirection.

    ← Return to question
    C4

    Are HLD, LLD, and deployment separate formal categories of software?

    They are common organizing viewpoints with community-dependent boundaries. HLD and LLD describe consequential structure at different detail; deployment locates runtime artifacts. They must agree about responsibility, ordering, and placement. A class diagram does not establish host redundancy.

    ← Return to question
    C5

    How can a system be available but lose data, or durable but temporarily unavailable?

    An application can keep accepting requests while acknowledging only volatile state, then lose that state after restart. A store can retain every committed row while refusing requests during recovery. Uptime measurements alone do not demonstrate durability, and retained data alone does not establish serving availability.

    ← Return to question
    S1

    The database commits task 7; the success response is lost; the client retries. Can the client safely assume the first operation failed?

    No. The timeout provides insufficient evidence about commit. A second unkeyed create may produce task 8. To bind repeated attempts to one intent, define a stable operation key, request fingerprint, atomic result storage, and retention behavior. Blind retries and a label saying “exactly once” do not supply that contract.

    ← Return to question
    S2

    Two adapters implement the same 80-character title limit. It changes to 200, but only one adapter is edited. What design change addresses the cause?

    Put the authoritative rule in the shared task service and have both adapters call it. Adapters still validate transport syntax and bound payloads. Repeating the edit in both adapters repairs this instance but preserves the duplication risk. Moving both adapters into different services would make coordinated changes harder.

    ← Return to question
    S3

    The team adds a second application host, each with its own local task database. What new failure has been introduced?

    Requests routed to different hosts can observe different task sets. Local persistence is not shared state or replication. The prior single-host assumption has changed, so review data placement, consistency, identity generation, and failure behavior. A load balancer cannot merge the two databases.

    ← Return to question
    D1

    Review this design: HTTP handler → shared dictionary → async file writer; the handler returns success immediately. Draw the failure and propose the smallest change that meets the restart promise.

    Failure trace: mutate dictionary, return success, crash before async writer commits; restart loses an acknowledged task. The minimal correction is to wait for an appropriate durable commit before reporting success, propagating write failures. A transaction-aware local repository is one feasible implementation. A queue alone only moves the durability boundary; its acknowledgment semantics would still need justification. Keep the modules in one deployment unless another requirement calls for distribution.

    ← Return to question
    I1

    Run examples/todo.py. Add a failing repository and prove that a failed insert never returns a Task. Then reopen the real store and prove a successful task remains.

    The service must propagate the repository exception; it must not manufacture a success object after failure. Use a repository whose insert raises OSError and assert create raises. With SQLiteTasks, create a task, close the connection, open a new connection to the same temporary path, and compare the stored record. Invalid titles must not insert any row. These tests exercise different promises; an in-memory double cannot demonstrate real persistence.

    ← Return to question
    T1

    The business now requires “no acknowledged task lost after the only disk is destroyed.” Can the current ADR stand? What evidence would a replacement need?

    The current ADR explicitly assumes intact committed storage, so its design is insufficient for the new requirement. Consider independent durable copies, acknowledgment rules, geographic or device failure correlation, backups versus live replication, and tested recovery. Asynchronous copying can lose recently acknowledged writes; copying corruption can preserve the wrong state. A replacement must specify the failure model and acceptable recovery behavior, then test its claims. More replicas without acknowledgment and independence rules do not establish the guarantee.
